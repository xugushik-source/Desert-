# DESERTO — Десерто — დესერტო

Площадка независимых кондитерских по городам. Независимый проект в репозитории `xugushik-source/Desert-`. Исходный SWEET HOUSE сохранён без изменений.

## Что реализовано

- Два тестовых города, три отдельные кондитерские, 36 исходных товарных карточек у каждой. Цены, остатки, варианты, расписание и вместимость интервалов принадлежат конкретной кондитерской.
- Витрина RU/KA/EN, поиск, категории, карточки, рекомендации дополнений, записка и получатель подарка. Отдельные сохраняемые корзины; очистку можно отменить.
- Один заказ относится к одной кондитерской. Смена города не переносит товары между продавцами. Время рассчитывается в часовом поясе города; целым тортам в тестовых данных требуется 24 часа.
- Серверный расчёт в целых тетри, проверка ожидаемой покупателем суммы, атомарное резервирование товаров и интервала. Повтор запроса с тем же ключом возвращает исходный заказ.
- Кабинеты владельца площадки, администратора кондитерской, сотрудника и курьера. Доступ через пароль и HttpOnly-сессию; приглашения одноразовые. Удалённый участник сразу теряет права.
- Подтверждение, подготовка, готовность, самовывоз; назначение курьера, получение, выезд и доставка. Второй курьер не может перехватить заказ. До назначения курьеру не показываются данные покупателя.
- Изменение состава и количества с причиной, первоначальным снимком и согласием покупателя. Изменение цены после предложения требует нового предложения.
- Отдельная запись проверенной оплаты, частичные платежи, долг, предотвращение повторного платежа. Доставка сама не подтверждает оплату. Отмена после начала приготовления списывает приготовленные позиции; предоплата переводится на проверку возврата.
- Управление городами и витринами владельцем, товарами и сотрудниками продавца, журнал событий заказа, показатели по завершённым заказам. Если себестоимость не задана, прибыль не выдумывается.
- События заказов записываются в outbox. Канал отключён: никаких ботов, рассылок и внешних платежей.

Все данные демонстрационные. Сведения о настоящих адресах, телефонах, остатках, себестоимости и аллергенах не придуманы. Имена продавцов и их присутствие в городе не подтверждают реальное партнёрство. Фотографии — оригиналы SWEETHOUSE-, происхождение в `public/media/ORIGIN.md`.

## Запуск без внешних сервисов

Нужен Node.js 24+. Зависимости для локальной работы и тестов не требуются.

```sh
git clone https://github.com/xugushik-source/Desert-.git
cd Desert-
git checkout feature/deserto-marketplace
npm test
npm run dev
```

Открыть `http://127.0.0.1:5173`. Кнопка «Кабинет» открывает вход. Случайный пароль владельца и локальный ключ восстановления создаются в `.runtime/local-access.json` с правами 0600. Они не выводятся в лог и исключены из Git. Данные переживают перезапуск в `.runtime/deserto.sqlite`. В кабинете владелец выбирает кондитерскую и выдаёт приглашение её администратору через «Команда». Администратор приглашает своих сотрудников и курьеров.

Покупательский доступ к заказу хранится в этом браузере. Ссылки и ключи доступа нельзя передавать посторонним. Восстановление через SMS/email пока не подключено.

## Новое независимое развёртывание

Сайт не развёрнут этой веткой. Старый SWEET HOUSE, его GitHub Pages и ТЖВЖИК не переключаются на этот Worker. Для DESERTO предназначены отдельные Worker `deserto-demo` и D1 `deserto-db`; чужие базы использовать нельзя.

После авторизации Cloudflare и разрешения на размещение нового демо:

```sh
npm ci
npx wrangler d1 create deserto-db
```

Вставить UUID НОВОЙ базы в `wrangler.jsonc`, затем:

```sh
npx wrangler d1 migrations apply deserto-db --remote
node tools/prepare-database.mjs
npx wrangler d1 execute deserto-db --remote --file .runtime/bootstrap.sql
npx wrangler secret put RECOVERY_SECRET
npm run build
npx wrangler deploy
```

Для `secret put` использовать ключ из `.runtime/deploy-access.json`, через защищённый ввод; тот же файл содержит доступ владельца для новой базы. Не публиковать этот файл и SQL bootstrap. Bootstrap предназначен только для пустой новой базы, повторно не запускать. Потеря/смена `RECOVERY_SECRET` меняет выдаваемые при повторе запроса ключи заказов, поэтому ключ нужно хранить надёжно. Случайные пароли в репозиторий не попадают.

Корневой GitHub Pages не исполняет Worker API и не является работающим предпросмотром DESERTO. На другом домене пути `/api`, `/app.js`, `/media` обслуживаются из корня нового Worker.

## Масштабирование и адаптация

Город и продавец — записи базы, а не отдельные копии сайта. Новую кондитерскую создаёт владелец в разделе «Площадка»; она появляется скрытой. Сначала добавить ассортимент, цену, расписание, адрес и команду, затем открыть витрину. Первый товар можно создать из общей демонстрационной заготовки, не имея доступа к чужому кабинету. Новым товарам назначаются новые идентификаторы и собственные остатки.

Оформление бренда: `public/index.html`, тексты `public/i18n.js`, палитра и эффекты `public/app.css`. Телефон/адрес/название конкретного продавца меняются в его кабинете. Данные миграций не переписывать для переименования бренда. Для другого независимого бизнеса создать отдельный Worker, D1 и ключи. Файлы `src/seed-products.json` и `tools/seed.mjs` содержат только стартовые тестовые данные.

## Границы этой версии

Это проверенная локальная реализация первой версии независимых витрин, а не заявление о готовности к приёму реальных заказов. Не подключены Telegram, Google Sheets, эквайринг, SMS/email, загрузка собственных фотографий, восстановление пароля, юридические документы, реальные зоны/стоимость доставки, касса/выдача денег курьерам, расходы/возвраты и расчёты с продавцами. Нет общего заказа из нескольких кондитерских и автоматического расчёта комиссии площадки. Пока поддержана валюта GEL. Шаблоны фотографий и категорий берутся из исходного ассортимента.

Демо-режим обозначен на всех страницах; он не отправляет заявки внешним получателям. Реальные контактные данные в демонстрационные заказы не вводить. Перед публичным запуском нужны проверка браузера, данные настоящих продавцов, правила обработки персональных данных и эксплуатационная настройка. Подробные результаты и ограничения проверки: `docs/TEST_REPORT.md`.

Обоснование светлой кремово-розовой гаммы, источники UX-исследований и границы выводов: [docs/DESIGN_RESEARCH_RU.md](docs/DESIGN_RESEARCH_RU.md).

## Закрытая размещённая демоверсия

https://deserto-bakeries-demo.sacredfinch8.chatgpt.site

Размещена через Sites с отдельной облачной D1 и доступом только владельцу через ChatGPT. Кнопка «Кабинет» использует защищённый вход владельца Sites; пароль из локальных файлов для этого не нужен. Вариант Worker для собственного Cloudflare сохраняет обычную парольную аутентификацию и не доверяет заголовкам браузера.

Дополнительный entrypoint `src/sites.mjs` предназначен только для owner-private Sites. Не переключать его на публичный доступ: сначала убрать первоначальную привязку владельца и провести отдельную проверку публичных прав. `tools/build-sites.mjs` упаковывает существующий интерфейс и миграцию без второй базы; `tools/check-hosted.mjs` — проверка тестовых заказов с секретами через скрытый stdin. В этой среде его запуску нужен флаг Node `--use-env-proxy`. Секреты хранятся в Sites, не в коде.

После добавления этого размещения локально проходят 20 тестов, включая привязку единственного владельца и атомарность стартовых данных. Автоматическая проверка браузера по-прежнему не выполнялась.

## GitHub Pages

Публичная витрина: https://xugushik-source.github.io/Desert-/

Workflow `.github/workflows/pages.yml` публикует `dist/pages` после проверок из `main`.
`node tools/build-pages.mjs` создаёт витрину с относительными путями: города,
отдельные кондитерские, поиск, категории, карточки, три языка и локальные корзины.
Экспорт строится только из новой синтетической базы, без пользователей и заказов.
На GitHub Pages нет Worker/D1: оформление, приглашения и кабинет показывают
объяснение, персональные данные и пароли не запрашиваются. Записи API запрещены.
Это публичная витрина, а не подтверждение работы серверных заказов на GitHub.

Полная серверная версия остаётся в `src/worker.mjs` и `wrangler.jsonc`.
Для неё нужен отдельный Cloudflare Worker/D1 и авторизация Cloudflare.
Не подключать GitHub-витрину к закрытому Sites-серверу и не публиковать его
служебные токены. После развёртывания собственного API отдельно настроить
доверенный origin, транспорт сессии и проверить весь путь заказа; простая
подстановка другого API URL недостаточна для безопасной авторизации.

## Акции, события и доход площадки

- «Выбрать торт» / «День рождения» / «Праздник»: выбор даты и сравнение целых
  тортов всех кондитерских выбранного города. Можно добавить один выбранный торт
  от каждой в её отдельную корзину; повторное нажатие не увеличивает количество.
  Дата переносится в оформление. Корзины разных продавцов пока оформляются
  отдельными заказами, единого списания/оплаты за несколько продавцов нет.
- Выдача `/api/vendors` сортируется сервером по сумме товаров завершённых и
  полностью оплаченных заказов за последние 30 дней, затем по их количеству и ID.
  Отменённые, неоплаченные, чужие города и возвраты на проверке исключаются.
  В статической Pages-витрине сохранён демонстрационный снимок без реальных продаж.
- Кабинет → «Акции»: администратор кондитерской предлагает скидку или подарок
  на свой товар, может остановить свою акцию. Владелец публикует после проверки
  всех расходов. Одна активная акция на товар, без срока автоматического окончания:
  действует до явной остановки. Товары с ценовыми опциями пока исключены.
  Цена скидки меняется в D1 атомарно, остановка возвращает исходную цену;
  существующие заказы сохраняют свою цену и подарок. Подарок — обещание
  исполнения в строке заказа; отдельной автоматической складской резервации
  произвольно названного подарка нет. Доступность подтверждает продавец/владелец.
- Кабинет владельца → «Доход площадки»: только завершённые и полностью оплаченные
  заказы. Все суммы в минимальных единицах валюты, расчёт только на сервере.
  **Чистый доход = сумма покупателя − выплата кондитерской − доставка − комиссии
  оплаты − упаковка − подарки − налоги − реклама − постоянные расходы − резерв
  возвратов/рисков − прочее. Минимум = округление вверх 10% суммы покупателя.**
  Неизвестные расходы блокируют проверку, подтверждённый ноль допустим.
  Ниже минимума сохраняется незакрытая недостача. Закрыть такой расчёт нельзя.
  Прогноз акции отделён от фактического расчёта. ПО проверяет введённые данные,
  но не подтверждает истинность расходов и не гарантирует прибыль бизнеса.
  Расчёт ничего не перечисляет и не списывает; это учёт, не эквайринг.
- Миграция `0002_promotions_settlements.sql` добавляет таблицы без удаления старых.
  Для Worker применить обе миграции перед новым кодом. Локальные инструменты
  применяют их автоматически; закрытая прежняя Sites-версия сама не обновляется.

Эти серверные функции доступны в исходниках и проверены локально. На GitHub
Pages кабинет/оформление по-прежнему ожидают отдельный подключённый сервер.

### Проверка 10% до принятия заказа

Миграция `0003_order_margin_gate.sql` добавляет условия выплат кондитерской и
подтверждённые лимиты всех остальных расходов на заказ. Владелец заполняет их в
«Доход площадки» → «Условия доходности заказов». Выплата кондитерской считается
от фактической стоимости товаров после скидки. Подарки учитываются дополнительно
по подтверждённому бюджету на каждую единицу.

Для `demo=0` отсутствие условий блокирует заказ. При наличии условий для любой
кондитерской сервер проверяет минимум 10% до резервирования и при согласовании
замены. Непроходящий заказ не сохраняется и не занимает остатки. Расчёт и версия
условий сохраняются атомарно с заказом. Изменение условий в ходе записи вызывает
откат. Суммы прибыли, присланные браузером, не используются. Демонстрационные
витрины без условий позволяют тестировать покупки и не заявляют реальную прибыль.
Условия и лимиты должны соответствовать действительным договорам и издержкам;
после завершения обязателен отдельный фактический расчёт с документами.
